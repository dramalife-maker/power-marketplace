# post-qa

和使用者**一起**找測試盲點，不要倒清單。流程：確認範圍 → 逐項 check 並討論 → 使用者點頭的才修。語言無關，依專案實際的測試框架與命名慣例對照。

## 流程

1. **確認範圍**：預設掃 **git unstaged 變更**（`git diff` 的檔案範圍），開工前用一句話跟使用者確認；只有當使用者明確指定目錄／檔案／commit 範圍時才改用指定範圍。
2. **先對齊「核心路徑」**：在跑 check 前，先列出範圍內可能屬於「壞了會出事」的核心路徑（金流、冪等、週期重置、權限、資料一致性等候選），請使用者圈選確認。**這是後續 Check A 與 E 的篩選基準**，避免追全覆蓋。
3. **逐項執行 5 項 check**，每做完一項先講發現、問是否列入修復，再繼續下一項。**不要一次倒完**。
4. **彙整共識清單**，請使用者選優先順序。
5. **一次只修一項**，修完讓使用者確認再下一項。

## 5 項 Check

- **A. 核心路徑上的公開純函式無測試**：限定**步驟 2 圈選的核心路徑**，找對外匯出（public / exported）且不依賴外部 IO（DB、cache、HTTP、檔案、log、時鐘、隨機）的單元，測試檔找不到對應測試者列出。**邊角函式不在此 check 範圍**（呼應策略 #3）。
- **B. 只驗「沒出錯」，沒驗行為**：測試只斷言 no error / 200 OK / truthy，沒驗回傳值、欄位、DB 狀態、發出的事件或副作用 → 等於沒測行為。
- **C. 測試環境 ≠ Production contract**：用 mock/stub/手動構造繞過真實建構路徑（略過 DI、resolver、middleware、retry/timeout 設定），測試通過卻與生產不一致，比沒測還危險。
- **D. 複雜分支缺 edge case**：多分支（if/else、switch、match、guard、early return）的函式，列出分支再對照測試是否覆蓋邊界值、空值、錯誤路徑。
- **E. 核心路徑無 E2E／整合測試守備**：對步驟 2 圈選的每條核心路徑，確認有對應的 E2E 或整合測試覆蓋「主要 happy path + 關鍵失敗模式」。沒有則列出。**只看核心路徑，不追全覆蓋**（直接落實策略 #3）。

## 測試策略（判斷嚴重度的基準）

1. **實作前先自我審查** — 列可能 bug、邊界值、安全風險，先擋低級錯誤。
2. **AI 寫測試、工程師審** — 禁止只測「沒出錯」，要驗業務結果（回傳值、持久化狀態、發出的事件、外部呼叫）。
3. **E2E 只守核心流程** — 不追全覆蓋，只守「壞了會出事」的關鍵路徑（金流、冪等、週期重置等）。
4. **對監控保持意識** — 關鍵失敗路徑必有結構化 log，欄位夠定位（user/order/rule id 等）；swallow error 要留上下文；partial failure 要明確標示。

## 操作原則

- **一問一答**：每次只提一個發現或問題，等回應。
- **只報告，不擅自修**：使用者點頭再動手。
- **具體**：每個問題給函式／類別名與檔案路徑。
- **附功能描述**：每個被點名的 func／方法，**必須附一句話描述它在做什麼**（例如：「`ClaimReward` 處理玩家領取獎勵，扣庫存後寫發放紀錄」）。判斷依據除了讀實作，**也要看 caller 的呼叫情境**——上下文常比函式本身更能反映真實用途與風險。沒看 caller 就只寫「不知道」，不要硬猜。
- **誠實**：某項沒問題就說沒問題，不硬湊。
