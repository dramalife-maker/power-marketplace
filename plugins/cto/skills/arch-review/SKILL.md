# 架構審查 Skill

## 概覽

此 skill 協助技術主管對工程師提交的設計方案進行有深度的技術審查，並自動整理摘要，
寫入對應工程師的 1on1 紀錄（路徑由 `~/.claude/plugins/cto/config.json` 決定）。

---

## Step 0：載入設定

讀取 `~/.claude/plugins/cto/config.json`：

- **若檔案存在**：取出 `1on1_dir` 作為本次 1on1 目錄路徑
- **若檔案不存在**：自動進入 `cto:setup` 設定流程，完成後再繼續審查

後續所有提到 `~/1on1` 的地方，皆以此設定值替換。

---

## Step 1：收集上下文

審查開始前，先確認以下資訊（若對話中已有則直接使用，不重複詢問）：

1. **工程師名字**：用於寫入 1on1 紀錄
2. **審查對象**：設計文件、程式碼草稿、PR diff，或混合
3. **專案標準來源**：
   - 優先讀取當前目錄或專案根目錄的 `CLAUDE.md`
   - 若無，詢問使用者是否有指定標準文件
   - 若都沒有，使用通用審查框架（見 references/general-criteria.md）

---

## Step 2：讀取專案標準

```
1. 嘗試讀取 ./CLAUDE.md 或 ~/CLAUDE.md
2. 從中提取審查相關的技術標準、架構原則、禁止事項
3. 若有專案 memory 紀錄（見 Step 5），也一併載入作為補充上下文
```

---

## Step 3：執行審查

根據輸入類型選擇審查角度：

### 設計文件 / 架構說明
- 邏輯正確性與完整性
- Scalability 與效能考量
- 遺漏的 edge case 與 failure mode
- 與現有系統的相容性
- 決策理由是否充分（有沒有評估過替代方案）

### 程式碼 / PR diff
- 邏輯正確性
- 效能影響（DB query、index 使用、N+1）
- 是否有更好的寫法
- 測試覆蓋是否足夠

**SQL 專項審查：**
若程式碼含有 SQL query（GORM、`db.Raw`、`tx.Exec`、migration），**必須 spawn `dba` agent** 進行專項審查，再將結果整合入審查意見。dba agent prompt 應包含：
- 每段 SQL 的等效語句與執行背景（哪個資料庫、transaction 內或外）
- 資料量量級的已知假設（若有）
- 要求回報安全性、效能（index、鎖競爭、N+1）、正確性問題，標示嚴重度（高/中/低）

### 輸出格式

審查結果以以下結構呈現：

```
## 審查摘要：<功能名稱>

### ✅ 做得好的地方
- ...

### ❌ 需要修正的問題
- [高] 問題描述 → 具體修法（檔案路徑、範例片段）
- [中] ...
- [低] ...

### ❓ 建議追問的問題（設計意圖不明、需作者說明的架構決策）
- ...

### 💡 整體評估
一段綜合判斷，包含這次審查觀察到的工程師思維模式。
```

> **注意**：使用 ❌ 而非 ⚠️ — ⚠️ 語意曖昧，❌ 明確表示「需要修正才能合併」。每個問題必須附上可操作的修法，不能只說「不好」。

---

## Step 4：確認是否寫入 1on1 紀錄

審查完成後：

- **若使用者已明確表示要寫入**（例如 args 中含「整理進去」、「寫入」、「記錄」）→ 直接執行，不再詢問
- **否則主動詢問**：

> 「審查完成。要將這次的摘要寫入 ~/1on1/<工程師名字>/ 嗎？」

等使用者確認後才執行寫入。

目錄結構、`index.md` 格式、`_notes.md` 格式、初次建立規則，見
`~/.claude/plugins/cto/references/1on1-writing-rules.md`。

### YYYY-MM.md 寫入格式

```markdown
## YYYY-MM-DD 架構審查：<功能名稱>

**背景**：<一句話說明這個功能的目的>

**工程師提案重點**：
- ...

**審查意見**：
- [高] ...
- [中] ...

**觀察到的思維模式**：
<這次審查中，工程師展現的決策習慣、盲點或成長跡象>

**後續追蹤**：
- [ ] <退回修改的項目或待確認事項>
```

### index.md 同步更新

每次寫入後新增一行，類型填 `架構審查`：

```
| YYYY-MM-DD | 架構審查 | <功能名稱> | [YYYY-MM](./YYYY-MM.md) |
```

---

## Step 5：更新專案 Memory

若此次審查發現了**針對該專案的特定審查重點**（非通用知識），
例如：「這個專案的 transfer_records 表有特殊的 index 結構需注意」，
則在審查結束後提示使用者：

> 「我發現了一些這個專案特有的審查重點，要更新到 memory 嗎？」

確認後，將內容以簡潔格式記錄至 memory，例如：
```
[專案名稱] 審查重點：transfer_records 查詢需確認有使用單欄 index on reference_code，
避免 composite index leftmost prefix 問題
```
